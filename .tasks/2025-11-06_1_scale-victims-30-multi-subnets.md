# 任务描述
将现有 victim 子网的容器节点总数扩充到 30 个，尽可能使用最轻量级的容器节点。新增节点需要同时满足：连接到 3 个不同的虚拟子网、这些节点之间保证双向连通性、并且所有新增节点均可访问 outer 子网。

# 项目概览
当前项目使用 docker compose v3 管理容器与网络拓扑：
内网 `inner`（IPv4: `172.16.238.0/24`，IPv6: `2001:3984:3989::/64`），外网 `outer`（IPv4: `10.0.10.0/24`）。
`gw` 容器作为网关，连接 `outer` 与 `inner`，并在启动命令中配置 `iptables` 将源自 `VICTIM_NET_RANGE` 的流量执行源 NAT（MASQUERADE），实现受害者子网对外访问。
已有 `victim-1` 与 `victim-2` 容器，均连接 `inner` 网络，并在启动命令中将默认路由切换到 `GW_INNER_IP`，以确保全部上行走 `gw`。`attacker` 容器连接 `outer`。
`inner` 网络启用 IPv6；`outer` 网络为 IPv4-only。`crs.env` 声明了各网段与关键静态地址。`up.sh`/`down.sh` 负责编排启动与停止。

# 分析
从现状看，victim 子网 `inner` 目前容纳两个受害者节点，网段 `/24` 足以扩充到 30 个节点。新增 28 个节点若继续使用 `c4pr1c3/crs-base`（基于 `alpine:3.16`），在镜像体量与运行时依赖方面较轻量，符合“最轻量”的要求（除非进一步改用更精简镜像并调整功能集）。

关于“新增节点连接到 3 个不同的虚拟子网，节点之间双向连通且均可访问 outer”：
现有 NAT 仅覆盖 `VICTIM_NET_RANGE`（即 `inner`）。若引入 3 个新子网（例如作为独立 `bridge` 网络），要实现它们对外访问，需要在 `gw` 增加对应源地址范围的 NAT 规则，并确保路由与转发开启。此外，若节点分布在不同子网且不共享同一 L2 网络，它们之间的双向连通需依赖 `gw` 进行三网互路由与策略放通；若每个节点同时加入这 3 个子网，则节点间可在任意共享子网直接二层互通，但这与“不同子网之间互通”的语义有所差异。

IPv6 目前仅在 `inner` 启用，`outer` 未启用 IPv6。若 3 个新子网需要 IPv6，则需在网络定义与 `gw` 的路由/NAT/转发策略中一并考虑；若仅需 IPv4，可保持与 `outer` 的一致性以简化实现。

当前 `gw` 的命令中含 `tcpdump -i inner-0 -n`，用于抓取 `inner` 接口流量。扩展多子网后，如需观测其互通与对外访问，可能需要拓展或调整抓包接口，但这属于后续验证与观测范围。

尚待澄清的关键点包括：新增 30 个节点是否包含已有 2 个（总数=30），或是在现有基础上额外增加到 32；“连接到 3 个不同的虚拟子网”是指每个新增节点同时加入 3 个子网，还是将全部节点按组分布到 3 个子网并要求跨子网互通；是否需要在这 3 个子网启用 IPv6；以及对网络命名与地址规划是否有偏好或限制。

已根据后续输入明确如下：
1. 总数增加到 32（在现有 2 个基础上新增 30）。
2. 新增节点分布在 3 个独立子网（每网约 10 个），并要求跨子网互通。
3. 仅需 IPv4 支持。
4. 新增节点只加入新的 3 个子网，不加入 `inner`。
5. “外网”是 `docker-compose.yml` 内的 `outer` 网络；要求新增节点可访问 `outer` 内的节点（出网方向）。
6. 镜像需进一步精简，仅保留网络联通性与联通性测试工具（ping/traceroute/curl）。
7. 新增子网内节点接受动态 IP 分配。
8. 在 Compose 中引入可扩展的受害者服务以按需 scale。
9. 新子网命名沿用业务语义，例如 `victim-1`、`victim-2`、`victim-3`。
10. `gw` 上需要继续抓取所有子网流量。
